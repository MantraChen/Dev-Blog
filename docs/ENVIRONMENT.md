# 运行环境评估与低风险替换方案

评估日期：2026-10-25。决策原则：优化收益优先，数据、网址和功能损失最小。

## 建议

**近期保留现有部署，升级到 Node 24.22.1 或同一主版本的后续安全补丁，并上线本次修复。若博客独占服务器、没有 Windows 专属依赖，下一步优先选择 Ubuntu 24.04 LTS + systemd + Caddy + Node 24 + SQLite。**

保持 Astro、React、Drizzle ORM、SQLite、域名及全部文章 slug。先迁移运行环境，暂不同时更换框架、数据库、评论系统或域名。Linux 方案的主要收益是服务管理、权限隔离和部署自动化更直接；这里没有证据证明仅换操作系统就能显著提高页面速度。

## 方案比较

| 方案 | 改造与数据风险 | 收益 / 限制 | 决策 |
| --- | --- | --- | --- |
| 保留 Windows + NSSM | 最小；现有运维习惯与服务器保留 | 无新增迁移成本；仍需维护 Windows、NSSM、权限和重启策略 | 立即采用，先修代码和运行时 |
| Ubuntu LTS + systemd + Caddy | 低至中；改部署，数据库格式不变，原生依赖需在 Linux 重装 | 可直接用专用服务账户、只读代码目录、journald、自动重启；不需要额外数据库进程 | 博客独立部署时的首选替换 |
| Linux + Docker Compose | 中；需要镜像、容器数据卷和网络配置 | 构建交付更一致，适合已有容器运维；卷备份与权限仍要管理 | 已经熟悉 Docker 或需要可移植镜像时再选 |
| 托管 Node 服务 + 持久磁盘 | 中；需要确认持久盘、备份、睡眠、部署重启和地区 | 减少系统运维，但 SQLite 通常约束为单机持久盘，供应商价格和保障待核实 | 不愿维护服务器时再按预算选型 |
| Workers/边缘函数 + D1/远程数据库 | 高；原生 SQLite addon、本地文件和 Node worker 不能假定直接兼容 | 可用边缘设施，但必须修改存储与部署并迁移数据 | 不符合本次最小改动目标 |
| PostgreSQL + Redis | 高；改驱动、迁移与维护额外服务 | 适合多机写入、共享状态和实际并发瓶颈 | 当前缺乏需求，不引入 |

SQLite 官方将低至中等流量网站列为适用场景；多台主机共享数据库、较多并发写入才应评估客户端/服务器数据库。不要把 SQLite WAL 文件放在 NFS/SMB 上供多机共用。[SQLite 使用场景](https://sqlite.org/whentouse.html)、[WAL 限制](https://sqlite.org/wal.html)

Caddy 官方提供并推荐 Linux systemd 服务配置。[Caddy 服务管理](https://caddyserver.com/docs/running#linux-service) Ubuntu 24.04 LTS 标准安全维护至 2029 年；若新主机供应商已充分支持 26.04 LTS，也可在副本验证后使用它。[Ubuntu 24.04 生命周期](https://documentation.ubuntu.com/release-notes/24.04/)

Workers 的 Node 兼容层需要逐项检查受支持 API；本项目还依赖原生 addon、本地 WAL 和独立工作线程，因此不能只改一个适配器就直接迁移。[Workers Node 兼容文档](https://developers.cloudflare.com/workers/runtime-apis/nodejs/)

## 初始资源与验收门槛

小型个人博客可先试 **2 vCPU / 2 GiB RAM、本地 SSD**；这是待测起点，不是容量保证。若服务器本机安装依赖和构建，建议预留更多内存，或在相同平台的构建环境生成 release。磁盘至少容纳当前库、WAL、迁移前备份、FTS 索引、若干 release 和系统日志；不能按数据库文件大小单独估算。

在当前服务器的服务账户环境下执行 `npm run doctor`，取得不含密码值的版本、配置是否齐全、数据库一致性、待迁移项、备份和剩余空间报告。接着在候选主机用生产副本比较：

- 公开页面和搜索的 P50/P95、错误率、CPU、RSS、事件循环延迟；使用相同数据和请求负载。
- 中文短词、正文搜索、保存文章、登录退出、Giscus 挂载、HTTPS、CSP 和所有旧 URL。
- 服务重启恢复、磁盘占用、备份完整性和一次实际恢复；记录 RTO/RPO 后再决定是否切换。

没有这些数据前，不因“Linux 更快”而立即更换正在稳定运行的主机。当前可确定的速度收益来自分页、FTS 索引、渲染缓存及将搜索移出 HTTP 主线程。

## 保持数据和访问连续性的迁移顺序

1. 在新主机独立部署同一 commit，用 SQLite backup API 的副本演练迁移；**不要复制 Windows 的 node_modules**，在 Linux 执行 `npm ci` 和完整验证。
2. 保持现有 `howielog.com`、路由、slug、Giscus repo/mapping 不变；用 hosts/反向代理测试域名验证。真实测试访问与生产统计隔离。
3. 切换前暂停旧 webhook、管理写入和公开统计写入（最简单是短暂维护窗口停服务），做最终一致备份；校验备份 `integrity_check`，复制到新主机后再迁移。迁移期间不得两边同时写入。
4. 核对文章数量、内容、草稿/隐藏状态、汇总访问和反应数；启用 HTTPS 并验证 `/api/health` 中的 release，然后再切换代理/DNS。DNS 缓存期间旧站保持维护或代理到新站，避免分叉写入。
5. 原服务器和最终备份保留一个已约定的回退窗口。新站产生写入后，回退必须先停写并迁回**最新**数据库；不能直接恢复旧快照，否则会丢失切换后的文章和统计。
6. 本次汇总表和触发器保留累计数字。自动保留策略会删除过期原始明细，旧版本代码只能数原始记录，所以清理后不能用旧版统计页面作为完整总数依据；回退优先使用能读取汇总表的版本。

`deploy/linux/dev-blog.service` 提供专用账户、回环绑定和只读代码目录的 systemd 模板。模板必须按 [Linux 部署说明](../deploy/linux/README.md) 在候选主机验证后使用。本次没有购买服务器、迁移 DNS、修改线上服务或承诺零停机。
