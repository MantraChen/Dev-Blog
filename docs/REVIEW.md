## 性能观察

首轮 500 篇合成文章的全量正文读取约 10.6MB，新单页约 0.43MB，元数据查询约 69KB；渲染缓存降低重复解析。此轮另对 1,000 篇、每篇约 20,250 字符的合成内容比较稀有关键词计数查询（9 次中位数）：原 LIKE 扫描 **12.630ms**，FTS 候选 + LIKE 确认 **0.147ms**，两者均返回 1。这个对比不包括 worker 启动、分页行加载和网络时间，不代表生产 QPS/P95。

FTS 索引增加磁盘与写入维护成本。短查询、常见关键词和总数统计仍可能昂贵，worker 隔离和队列限制提供资源边界，不保证任意数据规模下都快速。首次生产迁移须测量索引建立时间与磁盘余量。

## 上线与回退

1. 先停旧 webhook，做生产库一致备份；旧部署工具可能仍执行覆盖式旧脚本。不要只合并 main 就视为完成上线。
2. 更新到 Node 24.22.1+（同主版本），配置绝对 DATABASE_PATH、ADMIN_PASSWORD_HASH、HOST=127.0.0.1，检查 Caddy 转发和 ACL。详见 [Windows 部署说明](../deploy/setup.md)。
3. 用生产副本验证 005/006 迁移、汇总总数和 FTS 索引，再安排短暂维护窗口。后台保留策略启动后会删除过期原始明细，汇总保留；需保留迁移前备份。
4. 切换后核验 release 健康检查、原文章 URL、搜索、管理、统计和备份。故障优先回退到能读取汇总表的版本；不自动覆盖数据库，避免丢失新写入。
5. Linux 替换方案见 [环境评估](ENVIRONMENT.md)。建议先优化当前环境，再在独立候选主机验证；没有执行服务器购买、DNS 切换或生产迁移。

仍需用户侧完成的外部事项只有真实服务器上线/恢复演练、持续容量监控与 GitHub 账单解锁。匿名统计不是身份系统、SQLite 不是跨主机数据库、第三方评论有网络依赖，这些是明确保留的架构/产品边界。
